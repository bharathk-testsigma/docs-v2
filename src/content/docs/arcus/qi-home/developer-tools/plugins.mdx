A plugin captures what your developers do in their own tools and sends it to QI Home, where Arcus generates test cases from it.

There are 2 kinds. A **coding tool plugin** installs in Claude Code, Cursor, Codex, or GitHub Copilot, and captures prompts, tool calls, and file changes as a session happens. The **Arcus GitHub App** connects your repositories and captures every pull request your team raises.

<Aside type="note">
The GitHub Copilot plugin is the Arcus plugin for the GitHub Copilot CLI. [Testsigma Copilot](/arcus/automation/copilot/) is the test execution feature, and they are separate tools.
</Aside>

<Prerequisites>
- An active project in Arcus.
- The tool you are connecting, installed.
</Prerequisites>

Inside Arcus, every connection is visible in one place: on **QI Home**, click the more options icon (⋮), then **Manage integrations**. Connected plugins show **Active** under **Dev Tools and AI**, and each tool's setup link opens its install instructions.

## Connect a coding tool

Each coding tool follows the same 3 steps: install the plugin, sign in, and set the active project. The plugin sends nothing until you sign in.

Claude Code also needs Python 3.9 or later on your PATH as `python3`, since the plugin's lifecycle hooks are Python scripts. macOS and Linux ship with it. Configure Git locally before you start.

   claude plugin marketplace add testsigmahq/arcus-claude-plugin

2. Run `/arcus:login` and complete the SSO flow in the browser. You log in once per machine.
3. Run `/arcus:project list`, then `/arcus:project use <project_id>` to pin the project your sessions are sent to.

Context and test cases are pushed to the active project, so set it before you push.

<Aside type="note">
`/arcus:test` and `/arcus:push` also require the external [CLI](/arcus/qi-home/developer-tools/cli/) on your PATH. `testsigma login` authenticates the CLI so it can run test cases and report results; `/arcus:login` authenticates the plugin so Arcus can capture context. They are separate logins.
</Aside>

## Connect the Arcus GitHub App

You need admin access to the GitHub organization.

<Steps>

1. Go to the [Arcus GitHub App](https://github.com/apps/arcus-by-testsigma) and click **Install**.
2. Select the GitHub organization you want to connect.
3. Select **All repositories** under **Repository access**, or select specific repositories.
4. Click **Install & Authorize**.
5. Select the **Workspace** and **Project** in the **Connect GitHub** dialog that opens in Arcus.
6. Click **Connect**.

</Steps>

Every pull request raised in the connected repositories then flows into QI Home.

To check it worked:

<Steps>

1. Confirm the organization name and repository list show a **Connected** status under **Settings > Integrations > GitHub**.
2. Raise a test pull request.
3. Open **QI Home > Context Management**. The pull request appears on the **Unlinked Contexts** tab within a few seconds.

</Steps>

### Skip manual mapping with a tracker

Connect [Jira](/arcus/integrations/project-management/jira/) under **Settings > Integrations**, and any pull request whose title or description contains a ticket ID such as `PROJ-123` is mapped straight to the sprint holding that story. A pull request with a ticket ID does not appear in **Unlinked Contexts**, and you do not map it by hand.

<Aside type="note">
A pull request without a ticket ID lands in Unlinked Contexts whether the tracker is connected or not.
</Aside>

## Use the commands

The commands below are the Claude Code, GitHub Copilot, and Codex forms. Cursor uses hyphens instead of colons.

| Command | What it does |
|---|---|
| `/arcus:help` | Lists every Arcus command with a short explanation |
| `/arcus:login` | Signs you in to Arcus so it can capture your sessions |
| `/arcus:logout` | Signs you out and deletes the Arcus credentials stored on your machine |
| `/arcus:project list [search]` | Lists the Arcus projects you can access |
| `/arcus:project use <project_id>` | Sets the active project. Later events are attributed to it |
| `/arcus:project current` | Shows the pinned project |
| `/arcus:map ticket <KEY>` | Links a ticket (Jira, Azure DevOps, Linear, ClickUp, or GitHub) to the session, so it lands in the right sprint |
| `/arcus:test [feature]` | Authors end-to-end test cases for the current repository via the CLI, validates them, and prompts you to run them |
| `/arcus:push` | Pushes the test cases authored this session to Arcus, into a sprint or left unlinked |

## Map what arrives

Captured work doesn't become test cases until it is mapped:

- A **session or pull request** lands on the **Unlinked Contexts** tab of Context Management, unless it was mapped automatically. Mapping it to a sprint or an Adhoc session triggers generation from it.
- A **test case pushed with `/arcus:push`** lands on the **Unlinked Test Cases** tab. Linking it moves it into a sprint story, accepted, with its local run results carried over.

The mapping and linking flows are in [Context Management](/arcus/qi-home/context-management/).

## Control what is captured

A plugin transmits nothing until `/arcus:login` runs. After login it sends the session's prompts, tool calls, and captured file contents to Arcus. Sensitive credential files are always blocked (`.env*`, private keys, and anything under `~/.ssh`, `~/.gnupg`, or cloud credential stores), and dependency, build, and VCS directories are never captured. Your login tokens are stored in the OS keychain, not in plaintext on disk.

Each plugin's repository lists its full capture scope and its environment-variable controls.
