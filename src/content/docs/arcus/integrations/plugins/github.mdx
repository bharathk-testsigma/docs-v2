Connecting GitHub to Arcus by Testsigma surfaces in [QI Home](/arcus/qi-home/overview/) every pull request your team raises, where you map it to a sprint or an Ad-Hoc session. Arcus then generates or updates test cases from the code changes in that pull request. Developers don't change how they work.

<Prerequisites>
- An active project in Arcus by Testsigma.
- Admin access to the GitHub organization you want to connect.
</Prerequisites>

## Install the Arcus GitHub App

<Steps>

1. Go to the [Arcus GitHub App](https://github.com/apps/arcus-by-testsigma) and click **Install**.

2. Select the GitHub organization to connect.

3. Under **Repository access**, select **All repositories**, or choose specific repositories.

4. Click **Install & Authorize**. GitHub redirects you to Arcus.

5. In the **Connect GitHub** dialog, select the **Workspace** and **Project** to link this installation to.

6. Click **Connect**.

</Steps>

Pull requests raised in the connected repositories now appear in the **Unmapped Context** view in QI Home.

## Auto-map pull requests with Jira

With [Jira](/arcus/integrations/project-management/jira/) connected, a pull request whose title or description contains a Jira ticket ID such as `PROJ-123` is routed straight to the sprint holding that story. It never reaches **Unmapped Context**, and nobody maps it by hand.

<Steps>

1. In the left navigation, go to **Settings > Integrations**.

2. Under **Jira**, click **Connect** and complete the Jira connection flow.

</Steps>

<Aside type="note">
A pull request with no Jira ticket ID lands in **Unmapped Context** whether or not Jira is connected. Map it by hand from there.
</Aside>

## Verify the connection

<Steps>

1. In the left navigation, go to **Settings > Integrations**.

2. Under **GitHub**, confirm the organization name and repository list appear with a **Connected** status.

3. Raise a test pull request in one of the connected repositories.

4. Open **QI Home** and click **View** next to **Unmapped Context**. The pull request appears within a few seconds.

</Steps>

## View unmapped pull requests

<Steps>

1. In the left navigation, open **QI Home**.

2. In the QI Home sidebar, click **View** next to **Unmapped Context**. The **Unmapped Context** tab opens, with GitHub pull requests marked by the GitHub PR badge.

</Steps>

Each entry shows:

- **PR title**: the title of the pull request.
- **Repository**: the repository and branch the pull request is from.
- **Author**: the developer who opened it.
- **Lines changed**: lines added and removed.
- **Time**: when it was opened or last updated.
- **AI Suggestion**: the module Arcus recommends mapping it to.

## Map a pull request

<Steps>

1. On the pull request, click **Map to Module**.

2. In the **Map to Module** dialog, select the **Project**.

</Steps>

Then follow the path you need.

### Map to a sprint

<Steps>

1. Under **Map to**, select **Sprint**.

2. Select the **Sprint**.

3. Select the **Stories** within that sprint the pull request relates to.

4. Click **Map**.

</Steps>

The dialog's **What happens next** message reads "This PR will be mapped to the selected stories in the sprint and test cases will be auto-generated by Atto." Arcus triggers generation for that sprint, creating new test cases or updating existing ones from the pull request's changes.

### Map to an Ad-Hoc session

<Steps>

1. Under **Map to**, select **Adhoc**.

2. Under **Existing Adhoc Session**, select a session, or select **+ Create New Adhoc Session**.

3. Click **Map**.

</Steps>

## Map several pull requests at once

<Steps>

1. Select the checkboxes next to the pull requests you want to map. An action bar appears at the bottom, showing how many are selected.

2. Click **Map to Module**. The selected pull requests are listed at the top of the dialog.

3. Configure the mapping, then click **Map**.

</Steps>

## Dismiss a pull request

On a pull request that isn't relevant to your test coverage, click **Dismiss**. It is removed from the **Unmapped Context** list.

<Aside type="note">
Dismissed context doesn't contribute to coverage, and you can't recover it from this view.
</Aside>

## View mapped context

In the **Unmapped Context** view, click the **Mapped Context** tab. It shows:

- **Total Mapped**: how many context entries were mapped.
- **Tests Generated**: how many test cases came from mapped context.
- **Sprints Covered**: how many sprints received test updates from mapped context.

Each entry shows the sprint and story it was mapped to, and how many test cases were generated.
