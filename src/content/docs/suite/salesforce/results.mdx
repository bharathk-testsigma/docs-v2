Results are created for you as a Salesforce run executes, and **Run Results** is where you read them. The page drills down three levels: by test suite, by test case, and by test machine. A failed step carries the evidence captured at the moment it failed.

<Prerequisites>

- A test plan has executed at least once.
- For step screenshots, the plan captured them. **Failed Steps alone** is enough.

</Prerequisites>

## Find a run result

Go to **Run Results**. The list supports three controls.

| Control | What it offers |
| --- | --- |
| **Search** | Filters by any run result name containing your query |
| **Sort by** | **Title**, **Created Date**, **Updated Date**, or **Last Run**, ascending or descending |
| **Show Filters** | **Created By**, **Last Run Date**, **Created Date**, **Updated Date**, and **Labels** |

## Read results by test suite

Click the test plan you want. Suite level is the default view.

Expand a suite to see the test case results inside it. Icons on the suite row report how many suites run in parallel, and how many cases run in parallel within each.

## Read results by test case

Select **Test Cases** from the view dropdown to flatten every suite into one list.

Hover a failed test case for a short reason without leaving the list. Click it to open **Test Case Results**. Each step there carries its **Element Information**, **Test Data**, **Settings**, **Metadata**, and **Step Details**.

The third view, **Test Machines**, groups the run by executing machine. Use it when one browser fails and the others pass. Click a machine to expand the suites it ran.

<Aside type="note">
The machine view lists machines, not the cases inside them. To see a machine's test cases, switch to **Test Suites** and apply a **Test Machine** filter instead.
</Aside>

## Narrow a result with filters

A large plan result is easier to read filtered. Filters apply in three places on the page.

<Steps>

1. **Filter the runs** — Click the **Filters** icon on the **Test Runs** panel, set what you want, and click **Apply**.

2. **Filter the tests** — Choose **Test Cases**, **Suites**, or **Machines** from the view dropdown, click its **Filters** icon, and click **Apply**.

3. **Filter by status** — Click a status in the **Run Overview** donut. It filters on top of whatever you already applied.

</Steps>

## Inspect a failed step

Step icons tell you the state at a glance.

| Icon | Meaning |
| --- | --- |
| Green tick | Passed |
| Spinner | Executing |
| Grey circle | Queued |
| Red cross | Failed |
| Red slashed circle | Not executed, or stopped |

Open a failed step for the error message, the screenshot taken at the point of failure, and the element the step acted on. Click the screenshot to expand it; arrows move between steps.

<Aside type="tip">
A failure that arrives right after an org change is usually stale metadata rather than a broken test. Refresh the metadata and repair what it flags — see [Recover from a metadata refresh](/suite/salesforce/setup/connections/#recover-from-a-metadata-refresh).
</Aside>

## Read the run overview

**More details** opens the run summary. A donut chart splits total steps into **Queued**, **Passed**, **Failed**, **Not Executed**, and **Stopped**. Beside it sit the machine details and the run's start time, priority, type, and who executed it.

At plan level the same panel adds **Last Run** timings, the editable **Build**, execution type, and environment. It also reports the post plan hook result with its addon details.

An auto-heal badge beside a test case name reports how many steps were healed during the run — common after a Salesforce release shifts the Lightning markup. Healing is applied, not hidden — see [Auto Heal](/suite/salesforce/auto-heal/).

The **Test Runs** panel lists every run of this plan. Select another one to load its results in place.

## Re-run failed test cases

After an org fix or a configuration change, you rarely want the whole plan again. Each test case row carries a re-run icon, and the run header carries a **Re-Run** button for the whole result.

Clicking **Rerun** offers three scopes, then **Start execution** begins it.

| Scope | What it runs |
| --- | --- |
| **All Test Cases** | Every case in the selected run |
| **All Failed Test Cases** | Only the cases that failed |
| **Select Cases for Re-Run** | The cases you tick |

<Aside type="note">
A re-run executes your current test cases, not the versions that produced the original result. If someone edited a case since, you are testing something else.
</Aside>

Each run ID allows at most 10 reruns. Reruns accumulate against the original run rather than starting a fresh history, so spend them deliberately.

Once a rerun finishes, **Compare Run** opens the **Rerun** overlay. It sets the new result against the previous one at every level.

## Keyboard shortcuts

The Run Results page is faster from the keyboard, particularly when switching levels.

| Action | macOS | Windows |
| --- | --- | --- |
| Test case level | <kbd>Option</kbd> + <kbd>C</kbd> | <kbd>Alt</kbd> + <kbd>C</kbd> |
| Test suite level | <kbd>Option</kbd> + <kbd>S</kbd> | <kbd>Alt</kbd> + <kbd>S</kbd> |
| Test machine level | <kbd>Option</kbd> + <kbd>M</kbd> | <kbd>Alt</kbd> + <kbd>M</kbd> |
| Run history | <kbd>Option</kbd> + <kbd>H</kbd> | <kbd>Alt</kbd> + <kbd>H</kbd> |
| Filters | <kbd>Option</kbd> + <kbd>F</kbd> | <kbd>Alt</kbd> + <kbd>F</kbd> |
| Run overview | <kbd>Option</kbd> + <kbd>O</kbd> | <kbd>Alt</kbd> + <kbd>O</kbd> |
