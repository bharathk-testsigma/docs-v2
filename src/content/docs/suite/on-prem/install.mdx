## Requirements

### Machine

| Requirement | Specification |
| --- | --- |
| CPU | 16 core |
| RAM | 64 GB or more |
| Storage | Either 512 GB–2 TB as single storage, or 256 GB for the OS plus a mounted disk of 1 TB or more |
| Operating system | Ubuntu preferred. RHEL 9.x is the recommended alternative, and RHEL 8 is supported |

Scheduled image backups are recommended for either storage option.

### Database

| Requirement | Specification |
| --- | --- |
| CPU | 4 core |
| RAM | 32 GB |
| RDBMS | MySQL |
| Version | 8.0.x |

<Aside type="note">
Testsigma provides a MySQL container, so a separate database host is optional. If you would rather use a hosted MySQL, it has to meet the specification above. Confirm final memory and vCPU counts with Testsigma before you buy hardware.
</Aside>

### Machine configuration

- Install Ubuntu at the root, on a 256 GB machine.
- Mount a 2 TB or larger disk for storage, at `/data`.
- All software installs at the root, configured to use the mounted disk for storage.
- Any file system will do — pick what your team knows.
- RAID improves disk performance, and is optional.

### Backups

Back up every 24 hours and keep a week of history. Clean old data periodically to protect disk health and free space. Longer retention may need extra hardware, which you can attach to the existing mount point with LVM.

Your IT team owns these backups, taken as disk backups or as backups of the specific data folders.

### Network checks

Confirm the server machine has a working internet connection, then open what it needs.

If a firewall is in the way, allow `*.docker.com`, `*.amazon.com`, `*.amazonaws.com`, and `*.maven.org`. Add `*.sendgrid.com` to use Testsigma's mail service.

Unblock these ports if they are closed: 3307, 7010, 8080, 8082, 8084, 9090, 9095, 9096, 9097, 4201, 4203, 4211, and 4230. [Architecture](/suite/on-prem/architecture/) maps each one to its service.

### Other things worth knowing early

| Point | Detail |
| --- | --- |
| Agent operating system | The agent runs on Linux, Windows, or macOS, whichever you prefer |
| Windows machines | None are needed to operate the server |
| Hypervisor | The on-prem server is not a hypervisor-based installation |
| Final storage location | Screenshots, apps, and other permanent files live on the host server running the containers |
| Temporary files | Screenshots and similar may need periodic cleaning, depending on usage and disk space |
| Default domains | You get URLs ending in `testsigmaprivate.com`, such as `https://cx.testsigmaprivate.com` |
| Custom domains | Tell Testsigma **before** the build is generated — see [Custom domains](/suite/on-prem/custom-domains/) |
| Recorder on Chrome | You need to be able to enable developer mode and install the recorder unpacked |
| SMTP | Supply your own SMTP settings to use an internal mail server instead of Testsigma's |

## Deploy the compose file

Testsigma sends you `docker-compose.yml` files matching the configuration you requested. They define a multi-container application: a MySQL server, a global HTTPD server, a Faktory worker, and the UI services for each component.

<Steps>

1. **Install Docker** — Install Docker and Docker Compose on the server.

2. **Go to the file** — Open a terminal in the directory holding `docker-compose.yml`.

3. **Bring it up** — Run `docker-compose up`. The services start in the background and keep running after you close the terminal.

</Steps>

### Reach the application

Along with the compose files you get a list of URLs, of this shape:

```
<company_name>.testsigmaprivate.com
<company_name>-addon.testsigmaprivate.com
<company_name>-visualtesting.testsigmaprivate.com
```

Add the mappings to your `hosts` file. Once the containers are up you can also reach the application at the server's IP address on the port the compose file exposes — for a web service on port 80, that is `http://<server-ip>:80`.

### Stop and remove

`docker-compose down` stops and removes every container and network the compose file created.

## What the compose file defines

| Container | Image and notes |
| --- | --- |
| `testsigma_mysql` | `testsigmainc/onprem:mysql-<companyName>-trial-<Version>`, with a volume so data persists. You can point the compose file at your own MySQL instead |
| `testsigma_worker` | `testsigmainc/onprem:worker-<companyName>-trial-<Version>`, the Faktory worker service |
| `testsigma_load_balancer` | `testsigmainc/onprem:load-balancer-<companyName>-trial-<Version>`, the global HTTPD server. Carries environment variables for each component it serves, plus a volume |
| `testsigma_id_server_ui` | `testsigmainc/onprem:id-server-ui-<companyName>-trial-<Version>` — Identity Server UI |
| `testsigma_app_server_ui` | `testsigmainc/onprem:app-server-ui-<companyName>-trial-<Version>` — WebApp Server UI, pre-configured for hosting web applications and capturing screenshots |
| `testsigma_mobile_inspection_ui` | `testsigmainc/onprem:mobile-inspection-ui-<companyName>-trial-<Version>` — Groot Server UI, with an environment variable for a driver action host |
| `testsigma_addon_server_ui` | `testsigmainc/onprem:addon-server-ui-<companyName>-trial-<Version>` — Kibbutz UI |
| `testsigma_visual_testing_server` | Pre-configured for capturing and comparing screenshots during execution |

Every service joins a custom network named `testsigma-network`, and each has a health check with its own interval, timeout, and retry count.

## Post-installation checklist

Work through these to confirm the deployment is installed, configured, and behaving.

1. The recorder captures actions during testing.
2. Auto-heal is enabled and recovers as expected.
3. The import add-on is integrated and functioning.
4. Users can sign in with the default password and reach the system.
5. Users can reset that password and sign in with the new one.
6. The agent is active, connecting the system to the test environment.
7. A test case executes and its results are correct.
8. SMTP is configured for email.
9. Screenshots appear in execution reports.
10. No emails arrive from Testsigma cloud — the property must not be set to cloud.

### After an upgrade

<Steps>

1. **Stop the old agent** — Confirm it is no longer active.

2. **Hard refresh** — Press <kbd>Ctrl</kbd> + <kbd>Shift</kbd> + <kbd>R</kbd> to clear cached data and fully reload the application.

3. **Download the new agent** — Take the latest version from the application.

4. **Start it** — Extract the download and start the updated agent.

5. **Verify** — Check the agent's status and version number.

</Steps>

## Troubleshooting

### The application is not accessible

The usual cause is missing host entries. Open `/etc/hosts` on the server and add `<system-ip-address> <domain>` pairs for every service:

```
192.168.0.1 dev.testsigmaprivate.com
192.168.0.1 dev-id.testsigmaprivate.com
192.168.0.1 dev-addon.testsigmaprivate.com
192.168.0.1 dev-visualtesting.testsigmaprivate.com
192.168.0.1 dev-audit.testsigmaprivate.com
192.168.0.1 dev-mobilerecorder.testsigmaprivate.com
```

Put each entry on its own line. Combining them is a known source of stray binary characters that break resolution.

### The server refused to connect

Run `docker ps -a` in the installation folder and confirm every container is `Up`. For any container showing `Exited`, read its logs for the cause, then bring it back with `docker compose up -d`.

If containers will not stay up at all, force a restart policy across everything running:

```bash
docker update --restart unless-stopped $(docker ps -q)
```

### Read and share container logs

Follow one container's logs in the terminal, then press <kbd>Ctrl</kbd> + <kbd>C</kbd> to exit:

```bash
docker logs -f testsigma-app-server
```

To send logs to support, copy them out of the container first:

```bash
docker cp testsigma-app-server:/opt/logs <destination_location>/
```

<Tabs syncKey="os">
<TabItem label="macOS and Linux">

```bash
docker cp `docker ps | grep -i "testsigmahq/server" | awk '{print $1}'`:/opt/app/logs <destination_folder>
```

This assumes one container for the `testsigmahq/server` image. Remove old containers first, then zip the folder and send it on.

</TabItem>
<TabItem label="Windows">

Run `docker ps`, copy the container ID for the `testsigmahq/server` image, then:

```bash
docker cp <container_id>:/opt/app/logs <destination_folder>
```

Zip the copied folder and send it on.

</TabItem>
</Tabs>

### Network checks for a domain

Resolve the domain, then test the port and the HTTP response.

```bash
dig app-testsigma.yourcompany.com
nslookup app-testsigma.yourcompany.com
nc -vz <ip-address> 443
curl -H "Host: http://app-testsigma.yourcompany.com" http://<ip-address>:<port>/
```

`nc -vz` confirms the connection reaches that address and port at all, which separates a DNS problem from a firewall one.

### Ports are unavailable

If 9090 and 443 are taken, stop whatever holds them and start again. To clear a previous Testsigma:

```bash
sudo su
docker container kill $(docker ps -q)
```

If those processes cannot be stopped, change the ports for the Nginx container in `docker-compose.yml` and run `docker-compose up -d`.

### Docker login fails

Sign in to Docker Hub with `docker login -u testsigmaonprem`. Ask Testsigma support for the access token.

<Aside type="note">
Never paste a Docker Hub access token into a shared document or a ticket. Treat it as a password: request it from support, use it, and let your credential store keep it.
</Aside>

On Linux, credential problems are usually the credential helper — see Docker's [credentials management guide](https://docs.docker.com/desktop/get-started/#credentials-management-for-linux-users). For a stuck GPG password store, restart the agent:

```bash
gpgconf --kill gpg-agent
gpg-agent
```

### The compose file is unsupported

`Version in ./docker-compose.yml is unsupported` means the installed Docker Compose is too old. Remove it and install a version that supports the file's schema, taking the release you want from [Docker Compose releases](https://github.com/docker/compose/releases).

### Docker Desktop will not start on Windows

This is normally WSL. Install it, or read Docker's [WSL guide](https://docs.docker.com/desktop/windows/wsl/) for the alternatives.

```bash
wsl --install -d ubuntu
```

### Screenshots, imports, or exports fail

Almost always folder permissions inside the container, on `ts_app_server_data`.

<Steps>

1. **List the containers** — Run `sudo docker ps` and copy the app server's container ID.

2. **Go inside as root** — Run `docker exec -u root -it <CONTAINER_ID> /bin/sh`.

3. **Find the folder** — Run `cd /opt/app`.

4. **Fix ownership** — Run `chown -R tsuser:testsigma ts_app_server_data`.

5. **Retest** — Run a test case and confirm screenshots appear.

</Steps>

The folder name differs per container, so match it to the container you entered.

### Add-on upload is refused

A connection-refused or unknown-server error on add-on upload points at `/etc/hosts`. Split every Testsigma entry onto its own line, then `ping testing-addon.testsigmaprivate.com` and confirm it resolves and returns data. If it does not, try mapping `127.0.0.1`, then a static private or public IP, until ping answers.

### A new user cannot be added

Wrong IP mapping in `/etc/hosts` for the `id-server` URL. Correct the mapping.

### The application is slow

MySQL connection drops and slowdowns are usually connection limits and packet size. Add a `command` to the MySQL service in the compose file:

```yaml
testsigma_mysql:
  container_name: testsigma-mysql
  image: testsigmainc/onprem:mysql-<companyName>-<Version>
  platform: linux/x86_64
  restart: always
  volumes:
    - ./data/db_data:/var/lib/mysql
  environment:
    MYSQL_ROOT_PASSWORD: root
  command: --max_connections=1000 --max_allowed_packet=128M --sql_mode="STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION"
  ports:
    - '3307:3306'
  networks:
    - testsigma-network
```

### Clean up containers and images

```bash
docker rm $(docker ps -a -f status=exited -q)
docker rm <CONTAINER-ID>
docker rmi $(docker images -a -q)
docker rmi <ID>
```

## FAQs

**Why does Testsigma need so many ports?**

Each port belongs to a distinct micro-service running as its own Docker container, so the count follows the service set. The full mapping is in [Architecture](/suite/on-prem/architecture/). Note that MySQL is 3307 externally and 3306 inside its container.

**Which operating system should the server run?**

Ubuntu is preferred. RHEL 9.x is the recommended alternative and RHEL 8 is supported — for those, follow Docker's [RHEL installation guide](https://docs.docker.com/engine/install/rhel/).

**Can I use my own MySQL rather than the container?**

Yes. Map it in the compose file in place of `testsigma_mysql`, and make sure it meets the [database requirements](#database).

**The application will not load straight after `docker-compose up`.**

Give it up to three minutes. Nginx needs time to start, and the URL answers once it has.

**How much hardware do I actually need?**

Start from the [machine](#machine) and [database](#database) specifications, then confirm memory and vCPU counts with Testsigma. The recommendations are adjusted per customer, and installation cost moves with them.
