## Why the agent exists

The agent solves two problems.

**Running tests inside your network.** A corporate firewall keeps Testsigma's cloud away from applications deployed on a private network. The agent sits on a machine inside that network and relays communication between Suite and the local test machine over HTTPS, without opening the network up.

**Recording mobile tests locally.** The mobile recorder needs details from the app on a physical device — the attributes behind each button and field. Connect the device to the agent's machine and the agent feeds those details to your browser. The cloud recorder needs no setup but adds delay; the local recorder through the agent does not.

It ships with everything it needs: a bundled Java JRE, browser drivers, Appium and the mobile recorder libraries for Android and iOS, and the utilities for local execution and reporting.

The agent works in a pull model: it opens outbound connections to the Testsigma server, asks for work, and posts results. Nothing connects inward, so no inbound firewall rule is needed for the agent itself.

[Testsigma Terminal](/suite/installation/testsigma-terminal/) contains and manages an agent of its own. Installing Terminal detects an existing Java agent, upgrades it, and takes it over, and only one agent is ever active on a machine. Install the agent by itself when you want local execution without the desktop application, which is the usual case on a CI machine or a shared runner.

## Requirements

- **Memory:** 8 GB minimum, dedicated to tests.
- **Disk:** around 20 GB, including space for screenshots and downloaded files.
- **Processor:** dual-core or better.

If your network restricts outbound traffic or blocks downloads, allow HTTPS on port 443 to these domains.

| Purpose | Domain |
| --- | --- |
| The application and agent communication | `app.testsigma.com` |
| Testsigma Tunnel, used by the agent | `connect.testsigma.com` |
| Mobile recorder, used from the browser | `mobilerecorder.testsigma.com` |
| Assets, used by cloud and agent | `asset-proxy.testsigma.com` |
| Chat and ticket support portals | `*.freshchat.com`, `*.freshdesk.com` |

If your firewall filters by IP rather than domain, allow the IPs behind each domain above, plus the Lab IPs used for incoming connections during test runs: `35.174.92.188`, `34.204.63.14`, `74.50.105.97`. Ask support to confirm the current list before relying on it, since cloud IPs can change.

## Install the agent

Go to **Agents** and click **Download Agent**. Four formats are offered.

| Format | Use it when |
| --- | --- |
| ZIP | You want to control where the agent lives and how it starts |
| Executable (`exe`, `dmg`, `bin`) | You want a guided installer |
| Docker image | You are running the agent in a container |

For the ZIP, extract it into your home directory rather than a synced or system location.

<Aside type="note">
Keep the agent folder out of iCloud Drive, Google Drive, or any synced folder. Syncing corrupts agent files, and a system location drags in file permission and ownership problems.
</Aside>

### Start the agent as a process

Run it manually when you need it.

<Tabs syncKey="os">
<TabItem label="Windows">

Go to the installation folder and double-click `start.bat` (or `TestsigmaAgent.exe`), or run `start.bat` from the command line.

</TabItem>
<TabItem label="macOS or Linux">

Drag `start.sh` into a new terminal window and press **Return**.

</TabItem>
</Tabs>

Startup takes a few minutes. The agent then opens the **Agent Registration** page.

### Run the agent as a service

A service survives the terminal closing. From the installation folder, go to **Wrapper > Bin** and use the `TestsigmaAgent` command: `TestsigmaAgent start` on macOS or Linux, `TestsigmaAgent install` on Windows, `TestsigmaAgent stop` to stop.

```text title="TestsigmaAgent commands"
console       Launch in the current console.
start         Start in the background as a daemon process.
stop          Stop if running as a daemon or in another console.
restart       Stop if running and then start.
condrestart   Restart only if already running.
status        Query the current status.
install       Install to start automatically when system boots.
installstart  Install and start running as a daemon process.
remove        Uninstall.
dump          Request a Java thread dump if running.
```

<Aside type="note">
Starting automatically on boot is supported on Windows only. On macOS and Linux the service runs until the machine restarts, and then you start it again.
</Aside>

### Register the agent

<Steps>

1. **Open registration** — On the **Agent Registration** page, click **Register**. The agent's own UI is at `http://localhost:8383/agent` or `https://local.testsigmaagent.com:8484/agent/`.

2. **Describe the machine** — In the **Add new Agent** dialog, enter a **Name** and the maximum number of parallel sessions. The maximum cannot exceed the parallels available to your account.

3. **Set visibility** — Select **Public** to share the agent with your organisation, or **Private** to keep it to your account.

4. **Choose activation** — Select **Activate now**, or **Activate later** to register it without bringing it online.

5. **Finish** — Click **Register & Activate**. The agent appears on the **Agents** page with the browsers found on that machine.

</Steps>

The operating system version and browser names take a couple of minutes to appear. If they are still missing after ten, the agent started but did not report — check the [FAQs](#faqs).

To activate a deferred agent later, go to **Agents**, select it, and open **Config** for the activation command.

## Run the agent in Docker

Two routes work: register the agent in Suite first and pass its activation key to the container, or register a new agent as the container boots.

### With an activation key

Register an agent with **Activate later**, then go to **Agents**, select it, open **Config**, and copy the **Activation Key**. Set it as `TS_ACTIVATION_KEY`:

```yaml title="docker-compose.yml"
version: "3.9"
services:
  testsigma-agent:
    image: testsigmainc/testsigma-agent:latest
    container_name: testsigma-agent
    depends_on: [chrome, firefox, edge]
    volumes:
      - ./data/agent_data:/var/ts/agent
      - ./data/agent_temp:/tmp/agent_temp
      - ./<foldername>:/root/.testsigma/agent/logs
    environment:
      TS_ACTIVATION_KEY: "REPLACE_WITH_YOUR_ACTIVATION_KEY"
      CHROME: "http://chrome:4444"
      FIREFOX: "http://firefox:4444"
      EDGE: "http://edge:4444"

  chrome:
    image: selenium/standalone-chrome:latest
    shm_size: 1gb
    ports: ["4444:4444"]
    volumes: ["./data/agent_temp:/tmp/agent_temp"]

  firefox:
    image: selenium/standalone-firefox:latest
    shm_size: 1gb
    ports: ["4445:4444"]
    volumes: ["./data/agent_temp:/tmp/agent_temp"]

  edge:
    image: selenium/standalone-edge:latest
    shm_size: 1gb
    ports: ["4446:4444"]
    volumes: ["./data/agent_temp:/tmp/agent_temp"]
```

Save the file, then run `docker-compose up` from its directory. The agent detects browser versions through the `CHROME`, `FIREFOX`, and `EDGE` variables — all optional, so drop the services you do not test on.

Variants, from the same base file:

- **One browser only** — keep just that browser's service and environment variable.
- **Browsers on other machines** — drop the browser services and point `CHROME`/`FIREFOX`/`EDGE` at remote URLs, useful when one host lacks the resources for all containers.
- **Heap memory** — `MIN: "-Xms1g"` and `MAX: "-Xmx8g"` control the agent's heap; those values are the defaults.
- **ARM (Apple M-series)** — Google does not build Chrome for Linux ARM, so use the `seleniarm/standalone-chromium` and `seleniarm/standalone-firefox` images instead; Edge stays remote.

### Register while the container boots

Replace `TS_ACTIVATION_KEY` with auto-registration variables — the key comes from **Settings > API Keys**:

```yaml title="environment"
TS_AUTO_REGISTRATION_KEY: "REPLACE_WITH_API_KEY"
TS_AUTO_REGISTRATION_TITLE: "REPLACE_WITH_TITLE"
TS_AUTO_REGISTRATION_HTTP_PORT: "ANY_AVAILABLE_PORT"
TS_AUTO_REGISTRATION_HTTPS_PORT: "ANY_AVAILABLE_PORT"
```

## Connect a local Android device

The device has to trust the machine before Suite can see it.

<Steps>

1. **Reveal developer options** — On the device, open **Settings → About Phone → Software information** and tap **Build number** seven times.

2. **Enable USB debugging** — Open **Developer Options** from **Settings** and turn on **USB Debugging**.

3. **Attach and trust** — Connect the device to the machine running the agent. Accept **Allow USB Debugging**, and tick **Always allow from this computer** if it appears.

4. **Confirm in Suite** — Go to **Agents** and open the registered agent. The device is listed under **Devices**.

5. **Target it in a run** — Select the **Connected Machine** and the **Device** on the run form.

</Steps>

## Connect a local iOS device

iOS needs the same trust relationship, established through the machine rather than developer options. It also needs a provisioning profile: generate a certificate signing request under **Settings → iOS Settings**, upload it to your Apple Developer account, then upload the resulting certificate and provisioning profile back into Testsigma. With that in place, configure the device under **Settings → iOS Settings**, attach it to the agent machine, then find it under **Devices** on the agent's page. Target it by selecting **Local Devices** as the test lab and picking the machine and device.

## Trigger runs from another machine

An agent serves the whole account, so a test plan built against it runs from anywhere.

<Steps>

1. **Link the machine** — In the test plan's **Add Test Suites & Link Machine Profiles** step, click **Link Test Machine**, then **Add Machine**.

2. **Describe the profile** — Name it, select **Local Devices**, pick the active agent under **Connected Machine**, choose the **Browser**, and click **Create Profile**.

3. **Save and run** — Click **Save Selection**. Anyone on the account can now open this test plan on any machine and click **Run Now**; execution lands on the linked agent.

</Steps>

## Command-line arguments

Pass these when you start the agent from its installation directory, for example `./start.sh --TS_AUTO_DETECT_PROXY=true`.

<Aside type="note">
Pass arguments only on the **first** start. Later launches should just run the executable in the agent folder, or the argument set silently reverts to whatever you pass that time.
</Aside>

| Argument | What it does |
| --- | --- |
| `--TS_AUTO_DETECT_PROXY` | Detects and uses a network proxy, including one configured by a PAC file. Suits machines that move between networks |
| `--TS_USE_SYSTEM_PROXY` | Uses the operating system's configured proxy; combine with auto-detect as a fallback |
| `--TS_NON_PROXY_HOSTS` | Comma-separated hosts to reach directly, bypassing the proxy |
| `--TS_DELEGATE_SSL_VALIDATION` | Hands SSL validation to your inspection tool (Zscaler, Blue Coat) instead of Java, clearing `PKIX path building failed` errors |
| `--TS_TRUST_STORE_TYPE` | `JKS` (default), `PKCS12`, or `WINDOWS-ROOT` to use the Windows system certificate store |
| `--TS_ACTIVATION_KEY` | Activates an agent registered with **Activate later**, using the key from its **Config** page |
| `--TS_AUTO_REGISTRATION_KEY`, `--TS_AUTO_REGISTRATION_TITLE` | Registers and activates automatically on start, using an API key from **Settings > API Keys** and the given name |
| `--TS_AUTO_REGISTRATION_HTTP_PORT`, `--TS_AUTO_REGISTRATION_HTTPS_PORT` | Ports for auto-registration's internal communication |
| `--TS_MIN_MEMORY`, `--TS_MAX_MEMORY` | Heap floor and ceiling, in `m` or `g` — for example `--TS_MIN_MEMORY=1024m --TS_MAX_MEMORY=4g` |
| `--TS_IS_HEADLESS` | Runs browsers without a visible window |
| `--TS_IS_MOBILE_DISABLED` | Skips mobile device detection, freeing resources on web-only machines |
| `--TS_LOGGING_LEVEL` | `DEBUG`, `INFO` (default), `WARN`, or `ERROR` |
| `--TS_CHROME_PATH`, `--TS_EDGE_PATH`, `--TS_FIREFOX_PATH`, `--TS_IE_PATH` | Explicit browser executable paths, when detection misses an install or you need a specific version |
| `--TS_JAVA_HOME` | Path to the Java runtime the agent should use instead of the bundled one |
| `--TS_AGENT_JAR_PATH` | Path to `agent.jar` when it is kept in a custom directory |
| `--TS_ROOT_DIR`, `--TS_DATA_DIR` | Where the agent lives and where it stores its data |
| `--TS_ADDITIONAL_JVM_ARGS` | Extra JVM properties, quoted — `--TS_ADDITIONAL_JVM_ARGS="-Dlogging.file.name=/var/log/ts/agent.log"` |
| `--TS_ENABLE_GC_LOG` | Garbage-collection logging, for diagnosing memory issues |
| `--TS_ENABLE_HEAP_DUMP` | Writes a heap dump to the working directory if the agent crashes |

## Configure a proxy in args.yml

When the agent must use a proxy for most traffic but reach internal or trusted domains directly, set patterns in `args.yml`.

<Steps>

1. **Open the file** — In the agent's installation directory, open **agent_data/args.yml**.

2. **Add the bypass patterns** — Set both properties, separating domains with `|`:

   ```yaml
   http.nonProxyHosts: "localhost|127.0.0.1|*.testsigma.com|*.amazonaws.com|<internal-domain>"
   https.nonProxyHosts: "localhost|127.0.0.1|*.testsigma.com|*.amazonaws.com|<internal-domain>"
   ```

3. **Restart** — Save the file and restart the agent.

</Steps>

The full set of supported Java proxy properties: `http.proxyHost`, `http.proxyPort`, `http.proxyUser`, `http.proxyPassword`, and their `https.` equivalents.

## Set the log level and send logs

The log level controls what the agent writes to its CLI and local log files. `INFO` is the default; `ERROR`, `WARN`, `DEBUG`, `TRACE`, and `ALL` are the others, each adding detail.

To change it: open the agent from the **Agents** list, click the **Agent Settings** icon, choose the level, and **restart the agent** — the change does not apply until you do.

To send logs to support: hover the agent on **Agents**, click **Report Agent**, describe the problem, and click **Report**. The logs attach automatically. You can also collect them manually from the agent directory (see [Delete a corrupted agent](#delete-a-corrupted-agent-manually) for its location per OS).

## Keep the agent updated

Upgrades are automatic by default: when a new version releases, the agent downloads and installs it, resuming from scratch if the network drops mid-download. To take control, go to **Agents > Agent > Settings > Agent upgrade settings** and select **Manual** — the UI then shows `Current version: X.Y.Z. Latest version: A.B.C` and an **Upgrade** button when a release is out.

<Aside type="note">
If an upgrade arrives during an execution, it waits: the agent upgrades itself after the run completes.
</Aside>

### Update the agent manually

When auto-update fails — bad network, tight firewall — replace the installation.

<Steps>

1. **Stop the agent** — Run `stop.bat` (Windows) or `./stop.sh` (macOS/Linux) from the installation directory. The tray or status-bar icon disappears.

2. **Clear the folder** — Delete the contents of the `TestsigmaAgent` folder.

3. **Reinstall** — Download the latest ZIP from **Agents > Download Agent** and extract it into the same folder.

4. **Restart** — Run `start.bat` or `./start.sh` again.

</Steps>

### Update browser drivers manually

Driver files normally arrive with agent auto-updates. When that fails, download the driver matching your browser version — [ChromeDriver](https://sites.google.com/chromium.org/driver/), [GeckoDriver](https://github.com/mozilla/geckodriver/releases) for Firefox, [Edge Driver](https://developer.microsoft.com/en-us/microsoft-edge/tools/webdriver/) — and place it in the matching folder under the agent directory: `drivers/googlechrome`, `drivers/mozilla`, `drivers/edge`, or `drivers/internetexplorer` (Windows agents only).

## Retire and delete agents

A long agent list makes picking the right machine slow. Retiring an agent hides it without destroying it.

<Steps>

1. **Retire it** — On **Agents**, click the ellipsis beside the agent and click **Obsolete**, then confirm in the **Obsolete agent?** dialog.

2. **Or bring it back** — Click **Restore** beside an obsolete agent to reactivate it.

3. **Or delete it for good** — Click **Delete Permanently** on the same menu and confirm.

</Steps>

An obsolete agent cannot execute tests — that is the point of the state: on record, out of the picker.

### Delete a corrupted agent manually

If the agent pops up and closes immediately after an update — usually a conflict between `agent.UUID` in `agent.properties` and the system — clean it out completely.

<Steps>

1. **Quit it** — Click the Testsigma Agent icon in the system tray (Windows) or status bar (macOS/Linux) and choose **Quit**.

2. **Delete the pieces** — Remove the folder the agent started from, the agent's entry in the **Agents** list, and its configuration directory.

3. **Reinstall** — Download the latest agent and start it fresh.

</Steps>

| Operating system | Configuration directory |
| --- | --- |
| Windows | `%userprofile%\AppData\Roaming\Testsigma\Agent\config\` |
| Linux | `$HOME/.testsigma/agent/config/` |
| macOS | `$HOME/Library/Application Support/Testsigma/Agent/config/` |

## FAQs

**Do I need an agent for cloud runs?**

No. The agent exists only for execution on your own machines and devices. Runs on Testsigma Lab, BrowserStack, or Testsigma Emulator (Beta) never involve it.

**Does anything in my network have to accept inbound connections?**

No. The agent pulls: it queries the server for work and posts results back. Allow outbound HTTPS to `*.testsigma.com` on port 443 and nothing more.

**Why does the agent run Apache Tomcat?**

Tomcat is the local web server inside the agent. It hosts the agent's UI and holds the connection to the Testsigma server that test execution rides on.

**The agent will not start — "Port not available".**

Ports 8383 and 8484 are taken. Find the holder with `netstat -ano | findstr :8383` (Windows) or `lsof -i :8383` (macOS/Linux) and stop it — `taskkill /PID <pid> /F` or `kill <pid>`. Once the port frees, the agent detects it automatically.

**Startup fails with `java.net.BindException: Address already in use`.**

Another application holds Tomcat's ports (8080, 8005, 8009). Either free them the same way as above, or edit `server.xml` in the Tomcat working directory and move the agent to unused ports such as 8081, 8006, and 8010, then restart the machine and the agent.

**Startup fails with `BindException: Cannot assign requested address: JVM_Bind`.**

An IP conflict in your hosts file. Back it up, open it with admin rights, and comment out every `localhost` line except the defaults (`127.0.0.1 localhost` and `::1 localhost`). If that fixes it, confirm with your network administrator before deleting the line.

**Registration fails, or the OS blocks the agent.**

Allow the app in your privacy settings: **System Preferences > Security & Privacy > General** on macOS (allow App Store and identified developers), or **Allowed apps settings** on Windows.

**Registration says "app.testsigma.com is unreachable from the agent" and Register is disabled.**

The browser is blocking local network access. In Chrome, click the **Site Information** icon in the address bar, enable **Local network access** (click **Reset permissions** first if it was denied), refresh, and register again.

**My installed browsers are not detected.**

Find the executable path (`chrome://version` shows Chrome's) and start the agent once with it: `sudo sh start.sh --TS_CHROME_PATH=<path>` (macOS/Linux) or `start.bat --TS_CHROME_PATH=<path>` (Windows). The agent writes the path into `args.yml`, so later runs need nothing.

**Downloading the agent is blocked by our network.**

Whitelist the [required domains](#requirements). Inside the agent, `--TS_AUTO_DETECT_PROXY` and `--TS_DELEGATE_SSL_VALIDATION` address the two usual proxy and SSL-inspection causes.

**My tests sit in Queued forever on a local run.**

Check **Agents** first: if the agent's last request time is not within the last minute, it is not running. If it is, open the **Usage details** page and look for queued runs in **Test Plans & Dry Runs** — earlier runs may be holding your parallels. If neither explains it, send the agent logs to support with **Report Agent**.

**The recorder does not see my mobile device.**

In order: update the agent (auto-update can fail silently — [update it manually](#update-the-agent-manually)), swap the USB cable or port, and check the Wi-Fi signal if connected wirelessly. On Android, confirm USB debugging is on and `adb devices` lists the device; if you saw **Failed to install drivers**, give it time, check device storage, then uninstall the **AppiumSettings** and **UI Automator Server** apps from the device and restart the agent.

**A run fails with "Unable to create a new test session — Error while creating driver".**

Confirm the agent and device are both active under **Agents**, then re-run. If it persists, switch the run's **App details** between **Use path** and **Use details**, and finally uninstall and reinstall the app on the device. Still failing — send the test logs to support.

**The agent started but no operating system or browsers show up.**

Give it ten minutes. Past that, the agent is running but not reporting, and the log is where the reason is.

**Can other people in my organisation use my agent?**

Only if you registered it as **Public**. A **Private** agent is available to the account that registered it.

**How many parallel sessions can one agent take?**

You set the maximum when you register it, and it can be changed afterwards on the agent's own page. It cannot exceed the parallels on your account.

**Can the agent reach an application that is not on the public internet?**

Not on its own. That is what [Testsigma Tunnel](/suite/installation/testsigma-tunnel/) is for, and it solves the opposite problem: reaching your application rather than running on your machine.

**A run fails with "No route to host".**

The machine cannot download browser drivers because the network blocks the driver hosts. Whitelist `msedgedriver.microsoft.com`, `github.com/mozilla/geckodriver/releases/download/`, `storage.googleapis.com/chrome-for-testing-public/`, and `googlechromelabs.github.io`.
