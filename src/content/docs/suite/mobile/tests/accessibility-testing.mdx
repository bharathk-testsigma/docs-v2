Accessibility testing checks whether your Android or iOS application meets accessibility standards. You enable it per test step. The scan then captures the screen exactly where you want it checked, not at the end of a run.

<Prerequisites>

- **Web Accessibility Testing - Step Level** is enabled in **Settings → Preferences → Web Accessibility Testing**.
- You have a test case, a test suite, and a test plan with a test machine.

</Prerequisites>

## Enable it on test steps

<Steps>

1. **Open the test case** — Go to **Create Tests → Test Cases**, then open the case.

2. **Open step settings** — Hover the step, click the kebab menu, then **Step Settings**.

3. **Turn it on** — Select **Enable Accessibility Testing for the Step** and click **Update**.

4. **Repeat** — Do the same for every step you want scanned.

5. **Assemble the plan** — Add the cases to a suite, then the suite to a plan.

</Steps>

Two faster routes reach the same setting. **Bulk Select → Update Settings → Bulk Update Settings** does several steps at once. In the recorder, go to **Test Step → Step Settings**, then **Update**.

<Aside type="note">
Step groups support this too, by the same steps. It works on the **Test Authoring** page only. The recorder cannot configure a step group.
</Aside>

## Set the conformance level

<Steps>

1. **Turn it on** — While creating the plan, enable **Accessibility Testing** under **Additional Settings**.

2. **Pick a standard** — Expand **WCAG Versions & Conformance Level** and select your version.

3. **Run it** — Click **Run Now**.

</Steps>

## Read the report

When the plan finishes, click **View Reports**. Then click **View Report** in the bottom-right corner. The report has **Overview** and **All Issues** tabs.

**Overview** summarises the run. **Issue Overview** is a donut grouping findings as Critical, Serious, Moderate, Minor, or Success. **Issues by WCAG Principle** organises them under Perceivable, Operable, Understandable, and Robust. **Issues by Components** groups by native UI element type. That is how you spot one component failing across screens.

**All Issues** lists every violation. Its search, list, and detail pane match the web report — see [Work through All Issues](/suite/web/tests/accessibility-testing/#work-through-all-issues). **Compare Runs** and **Export** sit in the top-right corner.

## What is different from web

Two things only. Both follow from testing a native app, not a page.

- **Issues by Pages** does not appear, because there are no URLs to group by. **Issues by Components** carries that weight instead.
- **Element Details** shows the native code for the element, not HTML, and the screenshot is of the mobile screen.
