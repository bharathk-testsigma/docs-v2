Mobile runs target three kinds of hardware: Testsigma Lab's cloud devices, your own devices through [Testsigma Agent](/suite/installation/testsigma-agent/), and emulators or simulators on your machine. Cloud runs work like [web runs](/suite/web/run-tests/); this page covers the local routes.

<Prerequisites>

- The agent is installed, registered, and running, with the device [attached and trusted](/suite/installation/testsigma-agent/#connect-a-local-android-device).
- The test case or test plan exists.

</Prerequisites>

## Run on a local device

<Steps>

1. **Start the run** — On the test case, click **Run**.

2. **Target the device** — In the **Ad-Hoc Run** overlay, select **Local Devices** as the **Test Lab**, then pick the **Connected Machine** and the device.

3. **Adjust and go** — Change **Additional Settings & Desired Capabilities** if the run needs them, then click **Run Now**.

</Steps>

Local execution is the route for applications that never leave your network — the device, the agent, and the app all stay inside it.

## Run a test plan on local devices

A test plan reaches local devices through its machine profile.

<Steps>

1. **Open the machines step** — In the test plan, go to **Add Test Suites & Link Machine Profiles** and click **Link Test Machine**, then **Add Machine**.

2. **Describe the profile** — Name it, select **Local Devices** as the **Test Lab**, and pick the **Connected Machine** and device. Click **Create Profile**.

3. **Finish and run** — Complete the **Test Plan Settings**, click **Create**, then **Run Now**. Anyone on the account can trigger it from any machine — execution lands on the agent.

</Steps>

## Run in an emulator or simulator

No physical device is needed: an emulated device attached to the agent behaves like a real one, and several at once give you cross-device coverage.

<Steps>

1. **Start the emulator** — Install Android Studio, add a virtual device, and start it. On macOS, start a simulator from Xcode for iOS.

2. **Start the agent** — The running emulator appears to it as a connected device.

3. **Run against it** — In the **Ad-Hoc Run** overlay, select **Local Devices** and confirm the emulator is listed under **Test Machine**, then run.

</Steps>

## FAQs

**My runs sit in Queued for a long time.**

Every parallel your licence allows is in use, and the queue may be full too. **Dashboard → Usage details** shows both: `Parallel Tests 2/2` means both slots busy, `Queue 3/3` means the queue is also at capacity. Wait, stop something, or ask support about more parallels. On local runs, also confirm the agent is reporting — its last request time should be under a minute.

**"There are already running sessions for the user."**

A previous mobile recorder session is still alive — a forced page refresh leaves one orphaned, or another tab holds one. Orphans close themselves after 2 minutes; to act sooner, go to **Usage Details → Mobile Inspector Sessions** and stop the old session, then relaunch.

**The app force-closes or stops responding on cloud devices.**

Suite enables device capabilities by default that security-hardened apps treat as tampering — `testsigma.cameraImageInjection`, `testsigma.networkLogs`, `testsigma.allowTouchIdEnroll`, `testsigma.resigningEnabled`. Set the offending ones to `false` (Boolean) in the run's desired capabilities.

**Android app data resets between Close App and Launch App.**

Android-specific: restarting the app inside one session resets its data, which iOS automation does not do. A desired capability in **Test Environment Settings** preserves the data. {/* UNVERIFIED: the capability name is only in a screenshot in the legacy page — confirm it (likely an Appium noReset variant) */}

**My app will not record network logs, or throws certificate errors.**

Android apps distrust user-added certificate authorities by default, which blocks proxy capture. The app build must opt in: add a `network_security_config.xml` under `res/xml` with `<certificates src="system" />` and `<certificates src="user" />` as trust anchors, and reference it from the manifest's `<application>` element.

**Can I automate Apple Pay?**

Yes, through the built-in Apple Pay addon, on a specific device set only — iPhone XR through iPhone 15 on iOS 15–17. Verify the device against the compatibility list before building the flow.

**Entitlement or keychain errors on Testsigma's iOS devices.**

Re-signing with the wildcard provisioning profile strips most entitlements — only `application-identifier`, `team-identifier`, and `keychain-access-groups` survive. Apps that hardcode access groups hit `NSOSStatusErrorDomain Code=-34018`. Read those values programmatically instead of hardcoding them, build without the unsupported entitlements, or disable re-signing for enterprise-signed apps with `resignApp: false`.
