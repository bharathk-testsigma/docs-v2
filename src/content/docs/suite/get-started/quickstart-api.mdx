An API test needs no browser and no app build. You create a Rest API project, add a REST API step, send a request, and assert on what comes back. The same step type also works inside a web or mobile test case.

<Prerequisites>

- You have a Testsigma account.
- You have the endpoint URL, the method, and any authorization the request needs.

</Prerequisites>

This walkthrough uses [JSONPlaceholder](https://jsonplaceholder.typicode.com/), a free testing API, so you need no service of your own.

## Create a Rest API project

<Steps>

1. **Open the project form** — From the **Dashboard**, go to **Project** and click **New Project**.

2. **Set the application type** — Enter a **Project name**, then select **Rest API** from the **Application type** dropdown.

3. **Name the application** — Enter an **Application** name and a **Version**, then click **Create**.

</Steps>

Create a test case the usual way. Go to **Create Tests → Test Cases**, expand a **Feature**, then click the **+** icon beside a scenario.

## Build the request

<Steps>

1. **Add the step** — Click **Create Step** and type `/api` to select the **Rest API** step type.

2. **Enter the endpoint** — Set the URL. It is the base location plus the path, such as `https://jsonplaceholder.typicode.com/posts`.

3. **Pick the method** — **GET** is selected by default. The dropdown also offers **POST**, **PUT**, **PATCH**, and **DELETE**.

4. **Send it** — Click **Send**. The response appears at the bottom of the screen.

</Steps>

Parameters, headers, body data, and authorization each have their own tab. Fill only the ones your request needs.

<Aside type="tip">
Double-click the URL to insert a test data type, so one step covers many inputs. `https://@reqres.in/api/users?page=@page` parameterises both the host and the page number.
</Aside>

## Verify the response

A request that returns 200 is not a passing test until you assert on what it returned.

<Steps>

1. **Send the request** — The **response body** appears at the bottom of the screen.

2. **Add the verification** — Click **Outline**, then select **Add verification**. The field loads into the **Verification** tab.

3. **Choose a match type** — On the **Verification → Response Body** tab, pick how strictly the response must match.

</Steps>

Five verification types apply to both JSON and XML.

| Type | What it requires |
| --- | --- |
| **Strict** | Every specified condition matches exactly |
| **Strict Order** | Every condition matches, and in the specified order |
| **Lenient** | The essential conditions match; the rest can be relaxed |
| **Non-extensible** | Only the predefined rules apply, with no additions |
| **Schema** | The response matches a declared structure, format, and constraints |

## Store a value for later steps

Storing a value from the response lets a later step use it, which is how you chain requests.

<Steps>

1. **Open the outline** — With the response showing, click **Outline** and select **Store Variable**. It loads into the **Stored Variables** tab.

2. **Or store a header** — On the **Headers** tab, click **Store Variable**. Enter a variable name and the header name, then click **Create**.

</Steps>

## Run the test

Click **Run**, select a test machine on the **Ad-Hoc Run** panel, then click **Run Now**. Open the step in the result to see the request Suite sent and the response it received. A failure shows the error beside the response, which usually distinguishes a broken test from a broken endpoint.

<Aside type="note">
To reach a private endpoint, open the **REST API** step and go to **Settings**. Enter your tunnel in the **Tunnel Name** field. See [Testsigma Tunnel](/suite/installation/testsigma-tunnel/).
</Aside>

## FAQs

**How do I put dynamic data in a raw POST body?**

Reference a test data profile parameter as `"@|ParameterName|"` and a data generator as `"!|FunctionName(arguments)|"`, directly inside the JSON — `"id": "!|Number.digits(int:3)|", "name": "@|DogName|"`.

**My API test case fails. What are the usual causes?**

| Failure | Look for |
| --- | --- |
| Connectivity | Can the browser reach anything? Retry, then involve your network administrator |
| Invalid request URL | A path not starting with `/`, unmatched or empty `{}` braces, unencoded spaces (`%20`), or reserved characters (`; ? # $ * @ { } =`) in the path |
| Authorisation | Wrong or expired credentials on the request |
| Assertion mismatch | The response changed shape — re-check status, headers, and body assertions |
