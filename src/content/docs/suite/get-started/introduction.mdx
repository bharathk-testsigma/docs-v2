## Supported platforms

A project targets one application type. The type decides which steps, elements, and test labs are available to it.

| Application type | What it covers |
| --- | --- |
| Web application | Any browser application, including Shadow DOM, iframes, and image-based elements |
| Unified | One test case that runs on both Android and iOS. Modern stack only |
| Salesforce | Org-aware testing that reads your metadata, objects, and page layouts |
| Android | Native Android applications |
| iOS | Native iOS applications |
| Mobile web | A site in a mobile browser on a real device |
| Rest API | REST requests, as standalone tests or as steps inside a UI test |
| Desktop (Beta) | Windows applications built on UIA and SAP technologies, run through Testsigma Terminal |
| Windows (Lite) | Windows applications built on UWP, WinForms, WPF, or Win32, run through Testsigma Agent |

One test case can cross platforms. A flow that starts in a web application and finishes in a mobile application is a single test, not two.

Suite acts on the running application rather than its source, so the language, framework, and build tooling behind it do not matter.

## Test case structure

A test case is an ordered list of steps. Each step is an [NLP step](#terminology): a natural-language phrase bound to an element and an action.

```text title="NLP step"
Enter robert@gmail.com in the Email Address field
```

Because steps are readable, the people who know the product best can review a test without reading code. Because they are structured rather than free text, they still execute the same way every run. Steps also support conditionals, loops, reusable step groups, and REST API calls.

## Atto, the AI layer

Atto is the AI layer across Testsigma. It belongs to neither product alone, and the same agents work in Suite and Arcus. You do not open it as a separate tool: it surfaces inside **Atto's Home**, the recorder, the test case editor, and **Run Results**.

### Authoring

Atto turns a source into a test case. It reads a Jira requirement, a Confluence page, a Figma design, a spreadsheet, a video recording, an OpenAPI file, or a plain-language prompt.

Copilot works alongside you in the recorder and the test case editor. It generates steps for the screen in front of you, so you start from a draft rather than an empty test case.

### Maintenance

Broken locators are the usual reason a healthy suite decays. Auto-Healing compares the current UI against the stored locators and corrects invalid ones during execution. It reports every change it makes, so healing stays visible rather than silent.

### Analysis

When a step fails, the Analyzer agent identifies the error type, finds the root cause, and attaches the evidence captured during the run. The Bug Reporter agent files that into your tracker with the context already attached.

### What Atto reads

Generation starts from context rather than from a blank prompt. Atto reads any combination of these:

- **Requirements and tickets** — Jira, Confluence, Azure DevOps, XRay, and qTest.
- **Designs** — Figma files.
- **Files** — JPEG, PNG, GIF, PDF, DOCX, XLSX, and MD, up to five at a time.
- **Recordings** — up to ten video recordings, or a live recorder session.
- **API specifications** — OpenAPI and Swagger.
- **Plain language** — a prompt describing the flow you want covered.

Generated cases land in the **AI Generated Feature** folder as drafts, so nothing enters your suite unreviewed. For the full workflow, see [Atto](/suite/atto/overview/).

### The agents

Each agent owns one job. You do not invoke them by name; they run from the feature they belong to.

| Agent | What it does |
| --- | --- |
| Generator | Generates test cases from requirements, files, recordings, and prompts |
| Runner | Drives Copilot and Agentic Learning (Beta) execution |
| Healer | Corrects element locators that fail during execution |
| Analyzer | Diagnoses failed steps, and reports patterns and risk signals |
| Bug Reporter | Files bugs into your tracker from the analysis panel |
| Coverage Planner | Analyses test coverage across your application |
| Optimizer | Reports on test suite efficiency |

## Execution options

Four test labs are available, and any test case can run on any of them.

- **Testsigma Lab** — a managed set of operating systems, browsers, and real devices. Nothing to install.
- **Local Devices** — your own machines and attached devices, through [Testsigma Terminal](/suite/installation/testsigma-terminal/).
- **BrowserStack** — your existing BrowserStack account, connected as a lab.
- **Testsigma Emulator (Beta)** — a hosted emulator for faster mobile authoring.

A test case does not change when you change where it runs. The test lab is a run-time selection. To reach an application that is not on the public internet, use [Testsigma Tunnel](/suite/installation/testsigma-tunnel/).

## Execution stacks

An execution stack is the framework a project's tests actually run on. Suite has two: Classic and Modern. The stack decides which application types a project supports and how a run behaves, so it is worth knowing which one you are on.

### Stack comparison

Each row is a property of the stack itself, not of an individual test case.

| | Classic | Modern |
| --- | --- | --- |
| Framework | Selenium | Playwright (web) + WebDriverIO (mobile) |
| Language | Java | TypeScript |
| Unified Mobile | Not supported | Supported |
| Status | Legacy | Current |

### Modern stack components

Modern is not one framework. Three names show up in logs and error messages, so they are listed here rather than left to guesswork.

| Component | What it is |
| --- | --- |
| Playwright | The browser automation framework behind web runs |
| WebDriverIO (WDIO) | The TypeScript wrapper around Appium, used for mobile runs |
| BT Runner | The TypeScript execution framework that runs the steps |

### Application types that require Modern

Unified is the one application type that Classic cannot run. It is Modern only, because one test case executing on both Android and iOS depends on WebDriverIO.

<Aside type="note">
Unified Mobile is in progress as of July 2026, and several capabilities are deferred: Atto generation, local device execution, data-driven testing, scheduling, and CI/CD. Confirm the current state before you plan a Unified project.
</Aside>

## Bring your own key

BYOK (Bring Your Own Key) routes AI requests through a model you control. Suite accepts your own OpenAI, Azure OpenAI, Gemini AI, or Vertex AI keys, mapped per feature, so generation and analysis stay inside your own model governance. Features you leave unmapped use Testsigma's model providers. See [BYOK](/suite/atto/byok/).

<Aside type="note">
Generative AI features are gated behind an administrator preference. If Atto and Copilot are missing from your project, an administrator has not turned them on yet. Verified July 2026.
</Aside>

## Getting around

The left navigation carries the main sections: **Dashboard**, **Atto's Home**, **Create Tests**, **Test Data**, **Test Suites**, **Test Plans**, **Run Results**, **Settings**, and **Save Points**.

The Command Center does the same without the mouse. Press <kbd>Cmd</kbd> + <kbd>K</kbd> on macOS or <kbd>Ctrl</kbd> + <kbd>K</kbd> on Windows, type to search, then use the arrow keys and <kbd>Return</kbd>. It navigates, and it also adds users, shows recent test case failures, and opens support chat.

## Terminology

Suite names a lot of things, and several of the names are close enough to confuse. Every term below gets one sentence. Look here first when a label does not match what you expected.

### Test objects

These are the objects you create and organise. Each one is a thing you make, so it is lowercase in prose.

| Term | Definition |
| --- | --- |
| test case | An ordered list of steps that automates one scenario |
| test step | One action or assertion inside a test case |
| NLP step | A test step written in Testsigma's human-readable syntax |
| step group | A reusable sequence of steps shared across test cases |
| test suite | A group of test cases that run together |
| test plan | Links test suites to test machine profiles and settings |
| element | An item on screen that a step acts on, stored in the project's object repository |
| feature | The top folder in **Test Case Explorer**, holding scenarios |
| scenario | The folder inside a feature that holds test cases |

### Authoring and AI

Three features involve an agent driving your application, and they are not interchangeable. The table below is the fastest way to tell them apart.

| Term | Definition |
| --- | --- |
| Atto | The AI layer across Testsigma, spanning Suite and Arcus |
| Copilot | Executes the steps of an existing test case, pauses at debug points, and records new steps live |
| Run with Copilot | Executes automated steps generated by Atto and updates their locators |
| Agentic Learning (Beta) | Drives your live application from manual steps, then generates an automated test case |
| Auto-Healing | Corrects an element's locator automatically when it fails during execution |
| Test Recorder | Captures elements and actions from your application as steps |
| AI Generated Feature | The folder in Suite where every Atto-generated test case is saved |
| Chrome for Testing | The dedicated Chrome build used for Copilot and Agentic Learning sessions |
| Execution Point | Blue marker showing the step currently running |
| Debug Point | Red dot marking a step where execution pauses |

### Test data and environments

These decide what values a run uses and what it talks to.

| Term | Definition |
| --- | --- |
| test data profile | A set of input values a test case reads at run time |
| environment | A named set of variables, so one test case can run against QA, UAT, and staging |
| upload | A file stored in the project, such as an APK or IPA, that steps and runs can select |
| Mock Server | A Testsigma-hosted service that stands in for a real API |
| Desired Capabilities | Key, data type, and value triples that configure a run |

### Execution

These describe where a test runs and what happens when it fails.

| Term | Definition |
| --- | --- |
| ad-hoc run | A single test case run on its own, to check it works before you add it to a suite |
| dry run result | The result of an ad-hoc or Copilot run, kept with its screenshots and logs |
| test lab | Where a run executes: Testsigma Lab, Local Devices, BrowserStack, or Testsigma Emulator (Beta) |
| test machine | One operating system, browser, or device that a run targets |
| execution stack | The framework a project runs on, either Classic or Modern |
| Recovery Actions | Per-failure-type behaviour configured on a test plan |
| AfterTest Case | Steps that run after a test case regardless of its result |
| AfterTest Suite | A test case that runs after a suite completes, for teardown |

### Client applications

Two local applications extend Suite onto your own machine, and they do different jobs.

| Term | Definition |
| --- | --- |
| Testsigma Terminal | The desktop application required for Copilot recording and local device testing |
| Testsigma Agent | A local utility that orchestrates tests: queueing them, running them, and fetching results |
| Tunnel | Testsigma Tunnel, for reaching a locally hosted application from a cloud run |

### Extensibility

These add capability that the core product does not ship.

| Term | Definition |
| --- | --- |
| add-on | A custom extension that adds your own actions to Suite |
| plugin | A connection between Suite and a third-party tool, such as Jenkins or Slack |
| BYOK | Bring Your Own Key — using your own OpenAI, Azure OpenAI, Gemini AI, or Vertex AI keys for AI features |
