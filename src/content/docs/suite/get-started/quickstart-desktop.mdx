Desktop (Beta) automation starts from elements, not from a recording. There is no URL and no app upload. Testsigma Terminal attaches to an application already running on your Windows machine and reads its UI tree directly.

<Prerequisites>

- You have a Testsigma account.
- **Testsigma Terminal** is installed on your Windows machine.
- The **WinTest Automation** folder is present in the **Testsigma Agent** directory.
- The application you want to test is installed and open.

</Prerequisites>

Suite supports Windows applications built on **UIA** and **SAP** technologies.

## Create a desktop project

<Steps>

1. **Open the project form** — From the **Dashboard**, go to **Project** and click **New Project**.

2. **Set the application type** — Enter a **Project name**, then select **Desktop** from the **Application type** dropdown.

3. **Name the application** — Enter an **Application** name and a **Version**, then click **Create**.

</Steps>

## Capture the elements

A web recording captures actions and elements together. A desktop test does not, so capture the controls first and build steps on them afterwards. Two recorders do this, and both list what they find as a hierarchical tree.

<Steps>

1. **Open the element list** — Go to **Create Tests → Elements** and click **Record**.

2. **Pick a recorder** — In the **Desktop Element Recorder** dialog, select **Selective Element Recorder** for one control at a time, or **Batch Element Recorder** to take a whole window at once. Click **Launch**.

3. **Choose the application** — In the **Select Application** window, select your application and click **Start Recording**.

4. **Capture** — Click **Record**, then hover a control until it highlights green and click it. Batch mode takes the window without hovering.

5. **Check what you got** — Select an element name in the recorder and click **Locate Element** to highlight it in the live application.

</Steps>

<Aside type="tip">
Capture a few more controls than the test needs right now. A second pass costs more than the extra clicks, because the application has to be back in the same state. **Locate Element** is worth using before you close the recorder: a control captured from the wrong window looks fine in the tree.
</Aside>

## Create a test case

<Steps>

1. **Open the test case list** — Go to **Create Tests → Test Cases**.

2. **Pick a scenario** — In **Test Case Explorer**, expand the **Feature** and **Scenario** you want, then click the **+** icon next to the scenario.

3. **Name the test case** — Enter a name in the **Test Case Name** field and click **Create**. The **Test Case Details** page opens.

</Steps>

## Add the steps

<Steps>

1. **Open the action list** — On the **Test Case Details** page, select **Actions** from the dropdown.

2. **Choose an action** — Select the action you want from the **Actions** overlay.

3. **Bind an element** — Select one of the elements you captured, then pick one of the suggested actions.

</Steps>

Suite suggests actions from the element type, so a text field offers different actions from a button. That keeps each step valid for the control it acts on. Conditionals, loops, and step groups work here as they do elsewhere.

## Run the test

<Steps>

1. **Open the run panel** — Click **Run**. The **Ad-Hoc Run** panel opens.

2. **Choose the machine** — On the **Local Devices** tab, select your connected Windows machine.

3. **Start the run** — Click **Run Now**.

</Steps>

The run drives the application on your own machine, so leave it open and leave the machine unlocked until the run finishes.
