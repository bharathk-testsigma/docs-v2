Visual testing compares how a screen looks against a stored baseline image. It is off by default, and you turn it on per step rather than per test case. That keeps the comparison to the screens where appearance actually matters.

<Prerequisites>

- You have a test case with steps that reach the screens you want compared.
- You know which steps are worth comparing. Every enabled step stores an image.

</Prerequisites>

## Enable it on one step

<Steps>

1. **Open the step options** — Click the ellipsis icon on the test step.

2. **Turn it on** — Select **Enable Visual Testing**.

3. **Save** — Click **Update Step**.

</Steps>

## Enable it on several steps

<Steps>

1. **Select the steps** — Tick the checkbox beside each step you want compared.

2. **Open bulk settings** — Click **Update Settings** in the menu bar.

3. **Apply** — In the **Bulk Update Settings** overlay, tick **Enable Visual Testing** and click **Update**.

</Steps>

<Aside type="note">
Nothing is compared on the first run. Testsigma needs a baseline image for each enabled step, so visual testing starts reporting from the next successful run onward.
</Aside>

## Review the differences

Run the test case, then open the result. Each enabled step carries a camera icon: green means the current image matches the baseline, red means it does not.

Click the camera icon to open the **Visual Difference** overlay. It carries five controls.

| Control | What it does |
| --- | --- |
| **Highlight Differences** | Marks what changed, which is faster than comparing two images by eye |
| **Hide Visual Differences** | Conceals the markers again |
| **Select region to ignore from visual comparison** | Excludes an area from the comparison |
| **Merge base image and current image** | Overlays the two so you can see the shift |
| **Zoom in** and **Zoom out** | Inspect a detail closely |

**AI Insights** produces a UI Difference Analysis Report whenever differences are found. It names the likely cause of the mismatch and suggests a resolution, and you can copy the insight into a bug report.

## Tune the comparison

A pixel-exact comparison flags things you do not care about. Two settings fix that: how strictly images are compared, and which regions are skipped.

### Set the comparison mode

| Mode | How it compares |
| --- | --- |
| **Strict** | Full pixel-by-pixel comparison, requiring an exact match |
| **Lenient** | Pixel-by-pixel against a threshold — at 70%, it passes when 70% of pixels match and ignores the other 30% |

<Steps>

1. **Open the result** — Click **Ad-hoc Runs** in the **Utility Panel**, then **View Details**.

2. **Open the overlay** — Click the camera icon.

3. **Pick a mode** — Expand **Visual Testing Mode** and select **Strict** or **Lenient**.

4. **Set a threshold** — For **Lenient**, enter the percentage in **Threshold**.

</Steps>

To apply **Lenient** to one area rather than the whole image, click **Select region to highlight for visual comparison**, then expand the option and choose **Select selection**.

### Ignore a region

Ignoring a region keeps dynamic content out of the comparison — ads, timestamps, and user-specific data are the usual culprits behind false positives.

<Steps>

1. **Open the result** — Click **Ad-hoc Runs**, then **View Details**.

2. **Open the overlay** — Click the camera icon.

3. **Draw the region** — Select **Select region to ignore from visual comparison** and mark the areas to exclude.

4. **Save it** — Click **Save ignore region**.

</Steps>

## Fail a test case on a visual difference

By default a visual difference is reported but does not fail the test case. To change that, click **Test Case Settings** in the right navigation and enable **Fail Test Case if Visual Testing Fails**.

Turn this on only once the baselines and ignore regions are settled. Enabling it against noisy baselines turns every dynamic timestamp into a failed run.

## Accept a new baseline

When a UI change is intentional, the baseline is now wrong and every run will keep failing against it.

<Steps>

1. **Open the difference** — Click the camera icon on the step.

2. **Promote the current image** — At the top right, tick **Mark as base image** for the **Current Image**.

</Steps>

## Compare against a Figma design

Instead of comparing a run to a previous run, you can compare it to the design it was built from. The baseline becomes a Figma frame.

<Steps>

1. **Enable visual testing** — Click the kebab menu on the step, select **Enable Visual Testing**, then click **Update Step**.

2. **Open the Figma view** — Hover the step and click the camera icon to open **Visual Difference – Figma**.

3. **Add the design** — Under **Base Line Image**, click **Add Figma Designs**.

4. **Set the target device** — In **Add Devices**, select the **Browser** and **Resolution** to compare at.

5. **Link the frame** — Enter the Figma frame link in **Frame Link**, click **Refresh** to verify it, then click **Save**.

6. **Run and review** — Execute the test case, click the camera icon on the step result, and open the **Visual Difference – Figma** tab.

</Steps>

<Aside type="note">
Three things have to line up or the comparison is meaningless. The Figma frame dimensions must match the target resolution, and the **Browser** and **Resolution** set here must match what you pick on the **Ad-Hoc Run**. For Android and iOS, choose a mobile device rather than a browser.

Figma comparison covers web and mobile only, and it is limited to enterprise accounts. Contact Testsigma support to have it enabled.
</Aside>
