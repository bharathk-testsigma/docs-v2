Auto-healing is Testsigma's locator repair mechanism. When a step fails
because an element's locator no longer matches, auto-healing looks for the
same element by its other recorded attributes and, if it finds one match,
continues the run with the updated locator.

## How it works

Every element stores more than one locator — `id`, `xpath`, CSS, and the
attributes captured at recording time. When the primary locator fails,
auto-healing tries the alternatives in [locator precedence](/suite/test-authoring/elements/)
order. A step healed this way is marked in the run result, and the suggested
locator update waits for your review; nothing is rewritten silently.

Healing happens at run time only. Editing an element in the repository never
triggers it.

## When it applies

Auto-healing runs when the feature is enabled for the project and the step
uses a repository element (inline locators are never healed).

| Application type | Supported |
| ---------------- | ----------------------------------------------------- |
| Web              | Yes                                                    |
| Mobile           | Yes                                                    |
| Salesforce       | Yes                                                    |
| Windows          | No {/* UNVERIFIED: Windows Advanced healing support */} |

## What it does not do

- It does not create locators for elements that were never recorded.
- It does not heal a step when two or more candidate elements match — the
  step fails and the result names both candidates.
- It does not change the element repository until a reviewer accepts the
  suggestion.

<Aside type="tip">
Healing suggestions accumulate under **Elements** > **Review**. Accepting one
updates every test case that uses the element. Verified August 2026.
</Aside>

## Troubleshooting

### Steps heal on every run

The primary locator is stale, so each run repairs it again. Accept the
pending suggestion under **Elements** > **Review** to make the healed locator
primary.
